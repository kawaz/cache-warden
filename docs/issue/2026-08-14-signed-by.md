# signed-by constraint と暗号化永続化 (llm-gateway OAuth ストア要件)

## 概要

llm-gateway の OAuth クレデンシャル Store バックエンドとして cache-warden を使いたい、という kawaz 提案。要件は 3 点:

1. **signed-by constraint** — set 時の socket 対向アプリの署名 ID を記録し、同一署名アプリからのみ get 可能にする (DR-0030 Phase 2 の前倒し)。環境変数 / 平文ファイル / Keychain (同一ユーザのマルウェアに無力) の却下理由も記録する。
2. **暗号化を伴う永続化** — OAuth refresh token はローテーションされるため in-memory のみだと daemon 再起動で消失し、再認証 UX が劣化する。単なる API キーと違い永続化が必須。
3. **鍵管理に passkey PRF 拡張** — cw 起動時 or vault アクセス時に passkey で暗号鍵を導出して vault を復号し、set の度に暗号化永続化、get は in-memory で行う。

## 背景

統括評価 (2026-08-14): 方向性賛成・条件付き。論点:

- (a) signed-by は identifier 文字列一致でなく SecCode designated requirement (anchor+TeamID+identifier) 検証が必須、ad-hoc 署名偽装対策。dev build (未署名) の逃げ道設計が要る。macos-process-inspect crate への SecCode API 追加が前提 (issue `migrate-to-macos-process-inspect-crate` と連動)。
- (b) 永続化は per-entry / per-vault opt-in でインメモリ既定の設計思想と両立させる。RT ローテーションと durability 契約: 永続 entry の set ack = fsync 済み (write-then-rename) を意味論に明記しないと crash で新 RT が消失する。vault 形式は最小構成 (単一 AEAD vault + wrap された vault key) に絞る。
- (c) passkey PRF の native (AuthenticationServices) 対応可否は要裏取り。iCloud 同期 = 同期先デバイスでも復号可、の是非は裁定要。対抗案: Secure Enclave 鍵 + biometry ACL (デバイス固定・非エクスポート、機体喪失時は vault 全損だが再認証で回復可能なデータなので許容し得る) — こちらが本命の可能性あり。
- (d) **最大の構造論点**: ユーザ存在ゲート付き鍵で暗号化する以上、boot 時の無人 daemon 起動では vault を開けない。初回アクセス時プロンプト + それまで永続 entry は fail-closed、の運用を許容するか要裁定。

次の一手: PRF native 対応の文献調査 (着手中)、signed-by は永続化と独立に先行実装可能。

## 受け入れ条件
