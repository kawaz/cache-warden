# signed-by constraint と暗号化永続化 (llm-gateway OAuth ストア要件)

## draft-DR-0032 との整合 (統括 2026-08-14 精査)

`docs/decisions/draft-DR-0032-remote-approval-web-passkey.md` (2026-07-10 kawaz 裁定済み) が本 issue の議論の相当部分を既に決定している:

- (a) daemon 自身が承認ページを配信し daemon 自身が WebAuthn RP — assertion (PRF 出力含む) は同一 HTTPS セッションで daemon に届くため「ceremony 出力の受け渡し経路」問題は存在しない。追記 (10) の WebSocket/WebRTC/custom scheme 経路比較はこの決定により supersede される (経路の再導出だった)。
- (b) TLS 終端は daemon 責務外 (tailscale serve 等の外側に任せる裁定済み) — r124m9 の「caddy に管理させる」はこの裁定の別実装で整合。
- (c) RP ID / expected origin は config で受ける = RP ID 設定可は決定済み。ローカル開発は oreore.net の PoC 手順記載あり。
- (d) passkey 登録 ceremony のローカル TouchID 必須も DR-0032 で裁定済み (r124m5 はその再確認)。
- (e) リモート到達 = Tailscale (tailnet 限定 + ACL)、challenge lifecycle、first-response-wins 仕様化済み。

本 issue の新規部分 = vault 暗号化のみ。

次工程の DR 分割:
- **draft-DR-0033** = signed-by constraint (SecCode designated requirement 検証、独立先行可)
- **draft-DR-0034** = 暗号化永続 vault (DEK マルチスロット・CAS 調停・cw-owned/op-cached 区分・durability 契約。PRF unlock は DR-0032 の ceremony 基盤を拡張参照)

## 概要

llm-gateway の OAuth クレデンシャル Store バックエンドとして cache-warden を使いたい、という kawaz 提案。要件は 3 点:

1. **signed-by constraint** — set 時の socket 対向アプリの署名 ID を記録し、同一署名アプリからのみ get 可能にする (DR-0030 Phase 2 の前倒し)。環境変数 / 平文ファイル / Keychain (同一ユーザのマルウェアに無力) の却下理由も記録する。
2. **暗号化を伴う永続化** — OAuth refresh token はローテーションされるため in-memory のみだと daemon 再起動で消失し、再認証 UX が劣化する。単なる API キーと違い永続化が必須。
3. **鍵管理に passkey PRF 拡張** — cw 起動時 or vault アクセス時に passkey で暗号鍵を導出して vault を復号し、set の度に暗号化永続化、get は in-memory で行う。

## 背景

統括評価 (2026-08-14): 方向性賛成・条件付き。論点:

- (a) signed-by は identifier 文字列一致でなく SecCode designated requirement (anchor+TeamID+identifier) 検証が必須、ad-hoc 署名偽装対策。dev build (未署名) の逃げ道設計が要る。macos-process-inspect crate への SecCode API 追加が前提 (issue `migrate-to-macos-process-inspect-crate` と連動)。
- (b) 永続化は per-entry / per-vault opt-in でインメモリ既定の設計思想と両立させる。RT ローテーションと durability 契約: 永続 entry の set ack = fsync 済み (write-then-rename) を意味論に明記しないと crash で新 RT が消失する。vault 形式は最小構成 (単一 AEAD vault + wrap された vault key) に絞る。
- (c) passkey PRF の native (AuthenticationServices) 対応可否は要裏取り。iCloud 同期 = 同期先デバイスでも復号可、の是非は裁定要。対抗案: Secure Enclave 鍵 + biometry ACL (デバイス固定・非エクスポート、機体喪失時は vault 全損だが再認証で回復可能なデータなので許容し得る) — こちらが本命の可能性あり。
- (d) **最大の構造論点**: ユーザ存在ゲート付き鍵で暗号化する以上、boot 時の無人 daemon 起動では vault を開けない。初回アクセス時プロンプト + それまで永続 entry は fail-closed、の運用を許容するか要裁定。

次の一手: PRF native 対応の文献調査 (着手中)、signed-by は永続化と独立に先行実装可能。

## kawaz 裁定・補足 (2026-08-13 ccmsg r124m4)

1. 署名なし dev build は非想定 — ローカルビルドも署名するフローを既に構築済み。signed-by は designated requirement 検証一本で設計してよい (dev build 逃げ道は不要)。
2. vault フォーマットのバージョン管理はやり切る方針。
3. passkey PRF は native (AuthenticationServices) 対応を問題視しない — Safari/Chrome のブラウザ経由 ceremony で実施する想定 (passkey 署名も同様)。
4. iCloud/1Password 同期のリスクはユーザ責務の整理。kawaz 自身は 1Password 管理で SPOF を理解の上で運用する。
5. 並行リフレッシュの調停が必要 — 同一クレデンシャルの refresh 2 並行は RT ローテーションを壊す。
6. TouchID は cw の中核に据えない — 無人起動 + リモート解除を考えると暗号化 vault で TouchID と緩く縁を切る。persist 付き entry は初回 op fetch 以降 cw の暗号化 vault が正本になり op へ 2 度とアクセスしない (op との縁切り)。

### 追記 (2026-08-13 ccmsg r124m5)

7. TouchID の重要ポイントは passkey 登録時のゲート — 登録前後に TouchID を挟むことで、ユーザの知らない経路で cw の設定ストアに第三者の passkey を勝手に登録されることを防ぐ (TouchID は runtime unlock でなく登録 ceremony の防壁として残す)。
8. refresh 調停は CAS 採用で裁定。同一プロセスチェックは無意味 — llm-gateway 内でも複数セッション/スレッドが同一クレデンシャルを共有し、cw から対向スレッドの区別は付かないため pid チェックは識別根拠を持たない。CAS は requester 識別に依存せず expected_version のみで調停が完結するのが利点。
9. ブラウザ経由 ceremony は cw 自身が passkey 利用のための serve を行う — 鍵素材の受け渡し経路問題は消える。

**統括 caveat**: WebAuthn の RP ID は port を含まないため RP ID=localhost だと同一ホストの別プロセスの localhost サーバも同 RP ID で assertion ceremony を要求可能 (ユーザが TouchID に応じれば PRF 出力を取得され得る)。「ceremony を起動できるのは cw の serve だけ」を RP ID の取り方 or cw だけが知る salt の混合で担保する設計論点として DR で明示する。関連 findings: `docs/findings/2026-08-14-passkey-prf-native-macos.md` (native PRF は macOS 15+ で可、SE+biometry 対抗案は「TouchID を中核にしない」方向と緊張関係)

### 追記 (2026-08-13 ccmsg r124m6)

10. ceremony ページの serve は cw から分離する (サーバ証明書管理を cw に持ち込まない)。RP ID は localhost 不可、適当な https FQDN に固定 (ユーザ設定可も検討)。出力の受け渡しは WebRTC data channel / WebSocket / custom app scheme のいずれかを検討。

統括評価追記: 経路比較 — WebSocket loopback (最軽量、https ページからの loopback は mixed content/PNA の localhost 特例依存) / WebRTC (重いがリモート解除と同一経路に育つ) / custom scheme (簡単だが scheme 登録は早い者勝ちで横取りリスク)。共通防御として「cw が ceremony 開始時に one-time token + ephemeral 公開鍵を URL に埋め、ページは PRF 出力をその鍵へ暗号化して返す」パターンを敷けば、経路選択は実装コストと将来性だけの問題に落ちる。統括推し: v1 (ローカル解除) = WebSocket loopback + 暗号化封筒、v2 (リモート解除) = WebRTC (シグナリング導入のタイミングで)。注意: RP ID を変更すると既存 credential は全て無効 (RP ID 束縛) のため「設定可能だが変更は再登録」の明記が必要。

### 追記 (2026-08-13 ccmsg r124m7)

11. RP ID 変更で credential 全滅の件、kawaz 案 = localhost で登録して移動時に `/.well-known` の関連サイト扱いを使えないか。統括回答 = それは WebAuthn L3 の Related Origin Requests (`/.well-known/webauthn`)。ROR で出来るのは「RP ID はそのまま別 origin からその credential を使う」ことで、credential の RP ID 付け替え (移行) は不可 (RP ID は登録時に恒久束縛)。さらに well-known は RP ID ドメインから https 取得されるため RP ID=localhost は ROR のアンカーになれない。正しい適用形 = 初日から kawaz 管理の安定ドメインを RP ID に固定し、ceremony ページの置き場 (origin) 側を ROR で複数許可して柔軟化する。ユーザ設定可にするのは RP ID でなく許可 origin リスト側に寄せると全滅問題自体が発生しない。裏取り結果 (2026-08-14 統括 web 調査): ROR はブラウザ全対応済み — Safari 18+ (2024) / Chrome・Edge 128+ / Firefox 152 (2026-05)。制約: 許可 origin は登録可能ドメイン名 5 個まで (cw 用途では実害なし)。重要な注意: passkey プロバイダ側の対応差があり、1Password は ROR 未対応との情報 (iCloud Keychain / Android は対応)。kawaz は passkey を 1Password 管理のため、ROR 前提設計だと 1Password 管理 passkey で ceremony が通らない可能性 — 実機確認要、通らなければ「origin を RP ID と同一に保つ単純構成 (ROR 不使用)」が安全側。参照: https://web.dev/articles/webauthn-related-origin-requests / https://passkeys.dev/docs/advanced/related-origins/ / https://www.1password.community/1password-at-home-31/webauthn-support-of-related-origin-requests-3739

### 追記 (2026-08-13 ccmsg r124m8)

12. kawaz 問い = 複数キーで復号可能な暗号で vault 鍵を二段暗号化し、RP ID 移行を全滅なしで段階的にできないか。統括回答 = envelope encryption (鍵ラップ + マルチスロット) が標準パターンとして確立 (LUKS キースロット / age 複数 recipient / 1Password と同型)。vault 本体はランダム DEK 1 本で AEAD 暗号化、DEK を複数 KEK (passkey-A PRF / passkey-B PRF / SE 鍵 / recovery code の異種混在可) で独立ラップして header に並べ、どれか 1 つで unwrap 可能。RP ID 移行 = 新 RP ID で新 passkey 登録 → 旧 passkey で unlock して DEK 取得 → 新 PRF で DEK を再ラップしスロット追加 (vault 再暗号化不要) → 移行後に旧スロット削除、で全滅なし段階移行が成立。recovery code スロットを最初から 1 本置けば全 passkey 喪失にも耐える。注意 2 点: (a) スロット削除 ≠ 失効 — 過去に DEK を知り得た者には無効。真の失効は DEK ローテーション (vault 再暗号化、小さいので安価) が必要で、スロット削除時に常に DEK ローテする設計が意味論単純。(b) スロットは OR 合成なので増えるほど窃取面も増える — スロット追加は passkey 登録と同じ TouchID ゲート対象にする

### 追記 (2026-08-13 ccmsg r124m9)

13. kawaz 裁定: (a) スロット削除≠失効、(b) OR 合成で窃取面が増える — 2 点とも「ちゃんとやれば問題ない」判定。設計と実装で漏れがないように進める (削除時は常に DEK ローテ、スロット追加は TouchID ゲート対象、を実装側で徹底)。実装は開発中 localhost RP で進めてよいが、kawaz の現実のクレデンシャルを localhost で登録する気はなく、caddy にローカル serve 用 https を管理させているのでそれを RP に使う。**したがって RP ID の設定変更可能は最初から必要**。

統括の設計帰結追記: RP ID をグローバル可変設定にすると、変更時に旧スロットが迷子になる (旧スロットは旧 RP ID で登録された credential のまま、config の rp_id だけ書き換えると unlock 時にどの RP ID で assertion を要求すべきか判別できなくなる)。解決方針 = 各キースロットに登録時の RP ID / credential ID を記録し、config の `rp_id` は「新規登録・ceremony に使う値」と定義する。この設計だと RP ID 変更は「新スロット追加フロー」へ自然に誘導され (新 RP ID で新規登録 → 旧 passkey で unlock して DEK 取得 → 新スロット追加、は項目 12 の移行手順そのまま)、既存スロットはスロットに記録された RP ID で unlock を継続できるため全滅しない。

次工程: draft-DR 起草に着手。

## 統括評価の追加論点 (2026-08-14)

- (a) refresh 調停は cw 側に置くのが筋。実装形は lease (要 stuck lock 回収) vs CAS (世代番号付き set、expected_version 不一致は新値を読んで再試行、ロック回収問題なし) — 統括推しは CAS、refresh の「古い値を前提に更新」意味論と正確に一致するため。
- (b) ブラウザ経由 ceremony の新設計面 — PRF 出力 (鍵素材) を daemon へ渡す経路 (localhost callback / extension / native messaging) は「誰が unlock を起動でき誰が鍵素材を受け取るか」という新しい攻撃面。リモート解除まで視野に入れると unlock がネットワーク形状になるため独立 DR で切るべき。
- (c) entry 所有権区分が必要 — persist = 縁切りを暗黙等値にすると op 正本の API キーを persist したユーザが古い値を掴み続ける事故が起きる。「cw-owned (cw 経由の更新が正本)」と「op-cached (op が正本、TTL 再 fetch)」を entry 属性として明示する。
